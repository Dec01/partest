# Permissions — four cells, not one 401

`request_permissions` is a single test-case type covering four different security
layers. A suite that checks "a request without a token gets 401" and calls the type
covered leaves three classes of bug in place.

## The antipattern

```python
# Permissions "covered"
await api.make_request("GET", "/items", headers={}, expected_status_code=401,
                       type=types.request_permissions)
```

One call, on the collection, unauthenticated. What it never touches:

| Missing | What ships broken |
|---|---|
| unauth on the **item**, not just the collection | a filter chain guarding `/items` but not `/items/{id}` |
| a **foreign object** the caller may not see | "this role may POST" is not "this role may read anyone's row" |
| a **disabled account** with a still-valid token | the account is off in the application, the token is fine, and the request succeeds |

## The four cells

All four record as `type=types.request_permissions`. Do not invent
`request_permissions_inactive` — a new required type changes the P1 matrix for every
subtype. Mark the cell with an Allure story, a tag, or the test id instead.

| Cell | Subject | Expected |
|---|---|---|
| `allow` | authenticated **and** entitled to this object and method | 2xx per your contract |
| `no_access` | authenticated, but the object is outside their scope | 403 (404 if your API hides existence) |
| `inactive` | same valid token, account disabled **in the application** | 403 |
| `unauth` | no session, or a broken bearer | 401 |

Three different layers: the security filter, the "user disabled" check, and ownership.
They fail in different components — which is exactly why one 401 proves nothing about
the other two.

## Building the cases

```python
from partest import access_cases, anonymous_headers, invalid_bearer_headers
from partest import TypesTestCases as types

cases = access_cases(
    "GET", "/items/{id}",
    allowed_headers=owner.headers.read,
    foreign_headers=other_user.headers.read,
    inactive_headers=disabled_user.headers.read,
)

@pytest.mark.parametrize("case", cases, ids=lambda c: c.id)
async def test_item_access(api_client, case, item_id):
    """Access to an item by cell."""
    await api_client.make_request(
        case.method, case.path,
        add_url1=f"/{item_id}",
        defining_url=case.path,
        headers=case.headers,
        expected_status_code=case.expected,
        type=case.test_type,
    )
```

`access_cases` only builds the cells you give headers for. A cell you cannot exercise
is left out rather than guessed — an open reference catalogue genuinely has no
`no_access` cell, and a case that passes for the wrong reason is worse than a gap.
Mark such cells N/A in the suite explicitly; do not let them vanish silently.

Two ways to be unauthenticated, and they take different code paths:

```python
anonymous_headers()        # no Authorization header at all
invalid_bearer_headers()   # syntactically valid, unusable token
```

## The `inactive` cell

Disable the account **in the application**, never in the identity provider —
disabling in the IdP invalidates tokens and tends to break the stand for everyone
else. The point of this cell is the opposite: a perfectly valid token whose account
the application refuses to serve.

Implement `UserActivity` with whatever your project has (an admin endpoint, a service
call) and always restore in a `finally`:

```python
from partest import UserActivity

class ApiUserActivity(UserActivity):
    def __init__(self, admin_client):
        self._client = admin_client

    async def set_active(self, user_id, active):
        await self._client.make_request(
            "PATCH", "/admin/users", add_url1=f"/{user_id}",
            json_data={"active": active}, expected_status_code=200,
        )

was_active = await activity.snapshot(user_id)
await activity.set_active(user_id, False)
try:
    ...  # the inactive cell
finally:
    await activity.set_active(user_id, was_active)
```

## Coverage

Unauthenticated access deserves at least a list, an item, and a write — not one GET on
a collection. Where a cell does not apply, say so in the suite rather than omitting it,
so the next reader can tell "not applicable" from "nobody wrote it".
